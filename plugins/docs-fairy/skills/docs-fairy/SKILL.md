# Docs Fairy

문서 요청의 primary policy입니다. 코드에서 검증한 사실만 문서에 적고, 수정 전에 진단을 보고해 승인을 받습니다.

## 핵심 계약: 진단 → 보고 → 승인 → 수정

문서는 코드보다 되돌리기 어렵습니다. 잘못된 코드는 테스트가 잡지만, 잘못된 문서는 독자가 믿고 따라 하기 전까지 아무도 모릅니다. 그래서 이 스킬은 두 단계로 일합니다.

1. **진단**: 무엇을 만들지/고칠지/지울지를 근거와 함께 요약 보고합니다. 이때 파일을 수정하지 않습니다.
2. **수정**: 사용자가 항목을 골라 승인하면 그 항목만 수정합니다.

예외: 사용자가 처음부터 명시적으로 "바로 고쳐/만들어"라고 했고 범위가 명확하면 진단 보고를 결과 보고로 합쳐도 됩니다. 신규 문서 1개 생성처럼 기존 내용을 덮어쓰지 않는 작업도 바로 진행할 수 있습니다. 기존 문서를 고치거나 지우는 작업은 항상 진단을 먼저 보고합니다.

### 진단 보고 형식

**불일치**(문서가 틀림 — 코드가 변경됐는데 문서는 옛날 내용)와 **누락**(신규 기능이 문서에 없음)을 별도 섹션으로 구분합니다. 독자에게 불일치는 "고칠 것", 누락은 "새로 쓸 것"이라 후속 작업의 성격이 다르기 때문입니다. 불일치를 먼저 배치합니다 — 틀린 문서가 없는 문서보다 해롭습니다.

```
## 문서 진단: <범위>

검사 범위 한 줄 + 결과 요약 한 줄 (예: "결과: 불일치 5건, 누락 1건"). 독자는 이
두 줄로 심각도를 파악한 뒤 표를 읽습니다.

### 불일치 (틀린 내용 — 따라 하면 실패)

| # | 문서 | 문제 | 근거 | 제안 |
|---|------|------|------|------|
| 1 | README.md:45 | `--verbose`가 `--debug`로 개명됐는데 문서는 옛 이름 | src/cli.ts:120 (커밋 abc1234) | 옵션 표의 행 교체 |

### 누락 (새 기능이 문서에 없음)

| # | 문서 | 문제 | 근거 | 제안 |
|---|------|------|------|------|
| 2 | README.md 옵션 표 | 새 `--quiet` 플래그가 문서 어디에도 없음 | src/cli.ts:131 | 옵션 표에 행 추가 |

번호를 골라주시면 해당 항목만 수정합니다. (예: "1, 3 진행" / "전부 진행")
```

근거 열이 핵심입니다. 모든 진단 항목은 코드 위치(파일:라인)나 커밋으로 검증 가능해야 합니다. "~인 것 같음" 수준의 항목은 표에 넣지 않습니다.

### 수정 후 결과 보고

승인받아 수정한 뒤에는 무엇을 어떻게 바꿨는지 보고합니다. 보고의 상세 수준은 변경 규모에 맞춥니다.

- 항목이 적으면(대략 10건 이하): 항목별로 "어느 문서의 무엇을 어떻게" 수준까지 상세히.
- 대규모면(큰 개발 뒤의 일괄 갱신 등): 문서별·유형별로 묶어 요약하고 대표 예시 몇 개만 상세히 보여줍니다. 수십 건을 전부 나열하면 사용자가 검토할 수 없으므로, 필요하면 diff 확인 방법(`git diff` 등)을 안내합니다. 이런 규모라면 애초에 진단 단계에서 묶음 단위로 나눠 승인받는 것을 먼저 제안합니다.

문서를 새로 만들었을 때의 결과 보고에서는 핵심 구조물(명령어 표, 옵션 표 등)을 산문으로 요약하지 말고 **문서에 넣은 표를 그대로 발췌해** 보여줍니다. 사용자는 대부분 보고만 보고 승인 여부를 정하므로, 보고에서 표가 안 보이면 문서에 표가 없다고 판단하게 됩니다.

## Router

요청의 주된 작업을 하나 선택하고 필요한 reference만 읽습니다.

| Mode | 요청 예 | 읽을 reference |
|---|---|---|
| `GENERATE` | README/아키텍처 문서/API·CLI 레퍼런스/CHANGELOG/런북을 새로 작성 | [문서 생성](references/generation.md) |
| `SYNC` | "문서가 코드랑 맞는지 확인", 코드 변경 후 문서 갱신 | [동기화와 감사](references/sync.md)의 `SYNC` |
| `AUDIT` | "문서 전체 점검해줘", 주기적 문서 감사 | [동기화와 감사](references/sync.md)의 `AUDIT` |
| `IMPROVE` | "문서 읽기 좋게 다듬어줘", 구조·명확성 개선 | [품질 개선](references/quality.md) |
| `SITE` | 문서 사이트 구축, Starlight/VitePress, 기존 사이트에 문서 통합 | [문서 사이트](references/site-starlight.md) |

작업이 여러 mode에 걸치면 primary 하나를 정하고 실제로 필요한 reference만 추가로 읽습니다. 예를 들어 "문서 사이트 만들고 API 레퍼런스도 채워줘"는 `SITE`가 primary, `GENERATE`가 보조입니다.

### 경량 요청

다음은 reference 없이 이 파일의 규칙만으로 바로 처리합니다.

- **지목된 오타·자잘한 수정** ("README 12번째 줄 오타 고쳐줘"): 범위가 명확한 단일 수정이므로 진단 보고 없이 바로 고치고 결과만 알립니다. 고치는 김에 발견한 다른 문제는 수정하지 말고 진단 항목으로만 보고합니다.
- **문서 번역**: 내용·구조는 그대로 두고 언어만 바꿉니다. 코드 식별자·명령어는 원문 유지, 대상 언어 관례(경어체 등)는 기존 문서를 따르고, 기존 문서를 대체할지 병렬 파일(`README.en.md` 등)로 둘지는 요청이 불명확하면 확인합니다.
- **문서 찾기·안내** ("온보딩 문서 어디 있어?"): read-only 조사로 위치와 한 줄 요약만 답합니다. 조사 중 낡은 내용을 발견하면 답과 함께 알리되 수정은 승인 후에 합니다.

## 공통 규칙

모든 mode에 적용됩니다.

**근거 기반 작성.** 문서에 적는 모든 사실(명령어, 옵션, 경로, 동작)은 코드·설정·테스트에서 직접 확인한 것이어야 합니다. 확인하지 못한 것은 적지 않거나, 꼭 필요하면 "확인 필요"로 표시해 사용자에게 묻습니다. 그럴듯하게 지어낸 설치 명령 하나가 문서 전체의 신뢰를 무너뜨립니다.

**언어와 인코딩.** 마크다운 파일명은 영어(kebab-case), 본문은 한국어, 인코딩은 UTF-8입니다. 단, 대상 프로젝트의 기존 문서가 일관되게 다른 언어를 쓰고 있다면 그 관례를 따르고, 전환하려면 사용자에게 먼저 확인합니다. 코드 식별자·명령어·기술 용어는 원문(영어)을 유지합니다.

**간결함 우선.** 짧고 정확한 문서가 길고 그럴듯한 문서를 이깁니다. 문장 수를 늘리는 수식어를 걷어내고, 나열형 정보는 표·목록으로 구조화합니다. "이 섹션을 지우면 독자가 곤란해지는가?"에 아니오라면 지웁니다.

**예제 중심.** 산문 설명보다 실행 가능한 명령어·코드 예제를 우선합니다. 예제는 반드시 실제로 동작하는지 확인한 것만 싣습니다. 실행해볼 수 있는 예제는 실행해보고, 아니면 코드와 대조해 검증합니다.

**기존 구조 존중.** 문서를 수정할 때는 그 문서의 기존 톤·구조·헤딩 스타일에 맞춥니다. 요청받지 않은 대규모 재구성은 진단 항목으로 제안만 합니다.

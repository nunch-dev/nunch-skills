# 품질 개선 (IMPROVE)

기존 문서의 구조·명확성·완결성을 높이는 작업입니다. 사실 불일치 검사(SYNC/AUDIT)와 달리, 여기서는 "맞는 내용이지만 읽기 어려운" 문서를 다룹니다. 사용자가 개선할 문서와 범위를 지정했으면 바로 수정하고, 넓은 점검에서 새로 발견한 항목은 진단 보고로 먼저 제안한 뒤 승인받아 수정합니다.

## 점검 순서

읽는 사람의 여정 순서로 점검합니다. 상위 문제를 두고 하위를 고치는 것은 낭비입니다.

1. **독자와 목적이 맞는가.** 이 문서는 누구를 위한 것인가? 한 문서가 초심자 튜토리얼과 전문가 레퍼런스를 동시에 하려 들면 분리를 제안합니다.
2. **구조가 여정을 따르는가.** 독자가 필요한 순서(개요→설치→사용→심화)로 배열됐는가. 헤딩만 읽어도 문서 지도가 그려지는가. 헤딩 레벨이 논리적 계층과 일치하는가.
3. **각 섹션이 값을 하는가.** 지워도 독자가 곤란하지 않은 섹션, 다른 문서와 중복되는 섹션은 삭제·통합을 제안합니다.
4. **문장이 간결한가.** 아래 목록으로 다듬습니다.

## 입문자용 설명 점검

입문자·비개발자 대상 tutorial이나 explanation은 다음을 추가로 확인합니다.

- 세부 사항보다 전체 흐름을 먼저 보여주는가.
- 시각 자료 하나가 핵심 개념 하나만 설명하고, 짧은 캡션만으로 무엇을 보여주는지 알 수 있는가.
- 낯선 기술 용어를 처음 등장할 때 쉬운 말로 정의하되 정확한 명칭도 남겼는가.
- 비유가 실제 동작을 왜곡하거나 중요한 제약을 숨기지 않는가.
- 그림과 짧은 문장이 정확한 설명을 대체하지 않고, 필요한 상세 문서로 이어지는가.
- 독자를 어린아이처럼 대하는 말투, 장식용 그림, 과도한 캐릭터·이모지를 쓰지 않았는가.

## 문장 다듬기

- **수식어 제거**: "매우", "간단히", "쉽게", "강력한" 같은 평가어는 정보가 없습니다. 삭제.
- **동작 중심**: "~할 수 있습니다" 나열보다 "~하려면 X를 실행합니다"로. 문서는 가능성 카탈로그가 아니라 행동 안내입니다.
- **한 문장 한 정보**: 접속사로 이어진 긴 문장은 분리.
- **번역투 제거**: "~에 대해", "~를 통해", 과도한 피동("~됩니다"의 남발)을 자연스러운 능동으로.
- **산문 → 구조**: 3개 이상 나열되는 정보(옵션, 단계, 비교)는 표나 목록으로. 반대로, 항목 1~2개짜리 목록은 산문으로 되돌립니다.

## 예제 강화

설명만 있고 예제가 없는 섹션이 최우선 개선 대상입니다.

- 개념 설명 옆에는 실행 가능한 최소 예제를 붙입니다. 예제는 코드와 대조해 검증한 것만.
- 예제에는 기대 출력을 함께: "이 명령을 실행하면 다음이 출력됩니다."
- placeholder는 명확하게: `<your-api-key>`처럼 꺾쇠로 표시하고, 실제 값처럼 보이는 가짜 값을 넣지 않습니다.

## 하지 않는 것

- **재작성 금지.** 개선은 국소 수정입니다. 문서 전체를 새 문체로 다시 쓰면 git 이력이 무의미해지고 리뷰가 불가능해집니다. 전면 재작성이 정말 필요하면 별도 진단 항목으로 제안하고 명시적 승인을 받습니다.
- **톤 통일 강요 금지.** 프로젝트 기존 문서의 톤(경어체/평어체, 용어 선택)을 따릅니다.
- **내용 추가는 근거 있을 때만.** "이런 섹션도 있으면 좋겠다"로 내용을 지어내지 않습니다. 코드에서 확인한 사실이 있을 때만 추가를 제안합니다.

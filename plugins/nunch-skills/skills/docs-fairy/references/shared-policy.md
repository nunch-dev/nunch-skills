# 문서 공통 정책

`docs-fairy`와 `docs-fairy-site`가 함께 사용하는 규범의 유일한 원본입니다. 두 스킬의 `SKILL.md`와 mode reference는 이 파일에 있는 조건을 반복 정의하지 않고 링크와 mode-specific delta만 둡니다. 충돌하는 문구가 있으면 사용자 지시, repository의 명시적 규칙, 이 정책, mode-specific delta 순으로 적용합니다.

## 변경 권한

- **WHEN** 사용자가 대상과 변경을 명시하면, 해당 스킬은 자신이 소유한 문서 surface 안에서만 변경합니다.
- **IF** 작업 중 요청에 없던 삭제·rename·전면 재작성·대규모 구조 변경이 필요해지면, exact 대상과 영향을 보여주고 별도 승인을 받습니다.
- **UNLESS** 사용자가 범위를 확대하지 않는 한, 인접 문제는 현재 변경에 섞지 않고 근거가 있는 진단 항목으로만 제시합니다.
- 승인받은 항목을 처리한다는 이유로 진단에 없던 변경이나 다른 package·애플리케이션 코드 수정으로 확대해서는 안 됩니다.

## 근거 계약

주장 유형마다 다음 source를 사용합니다.

| 주장 | 우선 근거 | 금지 |
|---|---|---|
| 현재 명령·옵션·경로·API·동작 | 코드, 설정, manifest, 테스트, 안전하게 실행한 명령 | 이름이나 관례만 보고 추정 |
| 변경 시점과 범위 | Git diff, commit, tag, release 자료 | 현재 코드에서 과거 시점 추정 |
| 결정 이유와 당시 제약 | ADR, issue, PR, 회의 기록, 사용자 설명 | 코드 형태에서 동기 창작 |
| 외부 framework·provider 계약 | 실행 시점 공식 문서와 설치 version | 오래된 예시를 최신 사실로 간주 |

근거를 확인하지 못한 사실이나 이유는 문서에 확정적으로 적지 않습니다. 독자에게 꼭 필요한 값이면 `확인 필요`로 표시하고 한 가지 질문을 합니다.

## 구조와 표현

- 새 문서 세트나 정보 구조는 필요한 경우 Diátaxis의 tutorial, how-to guide, reference, explanation 중 주된 독자 요구를 하나 선택합니다. 기존 국소 수정·번역·ADR·프로젝트 기록에는 재구성을 강요하지 않습니다.
- 사용자가 지정한 언어, 프로젝트의 일관된 기존 관례, 한국어 순으로 선택합니다.
- 기존 파일명과 생태계 표준명을 보존합니다. 관례가 없는 일반 신규 문서에만 영어 kebab-case를 fallback으로 사용합니다.
- 코드 식별자, 명령어, 경로, API·도구 이름, schema key와 번역하면 정밀도가 떨어지는 기술 용어는 원문을 유지합니다.
- 산문보다 검증된 실행 예제와 구조화된 표·목록을 우선합니다. 장식용 섹션과 근거 없는 마케팅 문구를 추가하지 않습니다.
- 기존 문서를 수정할 때는 기존 tone·heading·정보 구조를 존중합니다.

## 검증과 완료 판정

각 스킬은 자신이 소유한 surface에 맞는 검증을 모두 실행합니다.

1. 문서의 사실과 예제를 source에 다시 대조합니다.
2. 문서에 기재한 경로·명령·API의 실재를 확인합니다.
3. repository 또는 package에 관련 lint·link check·build가 있으면 실행합니다.
4. 실행 가능한 사용자 흐름은 실제 surface에서 확인합니다.
5. 변경 전후와 무관한 사용자 소유 상태가 보존됐는지 확인합니다.

**IF** 필수 검증이 실패했거나 실행할 수 없으면 완료라고 주장해서는 안 됩니다. 검증된 결과, 미검증 항목, 실패 근거와 다음 행동을 `partial success`로 보고합니다. 기술부채 기록은 실패한 hard gate를 통과로 바꾸지 않습니다.

## 결과 보고

결과에는 다음을 포함합니다.

- 생성·수정한 문서와 사용자에게 중요한 구조 변화
- 주장의 근거와 실행한 검증 결과
- `완료` 또는 `partial success` 판정 이유
- 승인되지 않아 수행하지 않은 변경과 남은 진단 항목
- 사용자가 검토해야 하는 핵심 표가 있으면 산문 요약 대신 실제 표 발췌

## 경계 예시

### 자동 진행

- 입력: “README의 설치 명령을 현재 package script에 맞춰 수정해줘.”
- 판단: 대상과 변경이 명시된 일반 문서 수정입니다.
- 행동: 명령 실재를 확인하고 README만 수정한 뒤 관련 검증을 실행합니다.

### 승인 대기

- 입력: “문서를 전체 점검해줘.”
- 판단: 조사 중 변경 후보를 새로 발견하는 요청입니다.
- 행동: 근거가 있는 진단 목록만 제시하고 사용자가 선택하기 전에는 파일을 수정하지 않습니다.

### 부분 성공

- 입력: “문서와 사이트를 모두 최신 상태로 만들어줘.”
- 판단: 일반 문서 검증 뒤 SITE handoff가 필요한 복합 요청입니다.
- 행동: SITE 필수 문서가 미검증이면 handoff를 중단하고 검증된 결과와 blocker를 보고합니다.

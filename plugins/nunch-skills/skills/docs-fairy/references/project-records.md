# 프로젝트 기록 (RECORD)

ADR, 의사결정 로그, 프로젝트 히스토리, 사고 기록처럼 시간이 지나도 프로젝트의 맥락을 보존해야 하는 문서를 다룹니다. 기록 문서는 사용법을 가르치는 콘텐츠가 아니므로 Diátaxis보다 각 기록 유형의 형식과 시간 순서를 우선합니다.

## 기록 원칙

**현재 상태와 과거 이유를 구분합니다.** 코드·설정·테스트는 현재 동작의 근거이고, git diff·커밋·태그·릴리스 노트는 변경 시점의 근거입니다. 결정 이유와 당시 제약은 기존 ADR·이슈·PR·회의 기록·사용자 설명에서만 가져옵니다. 코드 모양만 보고 "단순성을 위해", "성능 때문에" 같은 이유를 추정하지 않습니다.

**기존 기록을 덮어쓰지 않습니다.** 결정이 바뀌면 기존 ADR의 상태를 `Superseded`로 바꾸고 새 ADR을 연결합니다. 프로젝트 히스토리와 사고 기록의 과거 항목도 사실 오류를 바로잡는 경우가 아니면 삭제하거나 현재 관점으로 다시 쓰지 않습니다.

**커밋 목록이 아니라 의미를 기록합니다.** 프로젝트 히스토리는 모든 커밋을 나열하지 않고 사용자가 이해할 수 있는 기능·구조·운영상의 전환점으로 묶습니다. 각 항목에는 검증 가능한 날짜나 기간과 근거를 남깁니다.

## 공통 절차

1. 저장소의 기존 기록 위치, 파일명, 번호·상태 규칙을 먼저 찾습니다. 기존 관례가 없으면 ADR은 `docs/adr/`, 단일 프로젝트 히스토리는 `docs/project-history.md`, 사고 기록은 `docs/incidents/`를 기본 제안으로 사용합니다. 새 번호형 기록의 파일명은 [언어와 파일명](naming-and-locales.md)의 기존 패턴 우선 규칙을 따릅니다.
2. 요청을 아래 기록 유형 중 하나로 정하고 필요한 근거만 조사합니다.
3. 확인된 사실과 확인되지 않은 이유를 분리합니다. 핵심 맥락이 없으면 완성본을 지어내지 말고 확인된 내용과 필요한 질문을 먼저 보고합니다.
4. 기존 기록을 수정할 때는 SKILL.md의 진단·승인 계약을 따릅니다. 사용자가 현재 결정을 구체적으로 설명하며 새 기록 생성을 요청한 경우에는 그 설명을 근거로 바로 작성할 수 있습니다.
5. 날짜, 상태, 관련 문서·이슈·커밋 링크를 다시 확인하고 깨진 링크가 없는지 검증합니다.

## ADR

ADR 한 개는 결정 하나만 기록합니다. 사용자가 ADR 생성을 요청한 경우에만 작성하며, 아키텍처 문서를 생성한다는 이유로 자동 생성하지 않습니다. 프로젝트에 기존 템플릿이 있으면 그대로 따르고, 없으면 Nygard 형식의 핵심에 날짜와 근거를 더한 다음 양식을 사용합니다.

```markdown
# ADR-NNN: 결정 제목

- 상태: Proposed | Accepted | Superseded | Deprecated
- 날짜: YYYY-MM-DD

## 맥락
결정을 내려야 했던 문제와 당시 확인된 맥락·제약.

## 결정
선택한 방식과 적용 범위.

## 결과
예상되거나 확인된 장점, 비용, 위험, 후속 작업.

## 근거
관련 이슈, PR, 커밋, 문서 링크.
```

다음 MADR 항목은 실제 기록이나 사용자 설명으로 확인된 경우에만 추가합니다.

- 결정 동인
- 검토한 대안과 각 대안의 장단점
- 관련 ADR
- 결정자

번호는 기존 ADR의 다음 번호를 사용합니다. 기존 식별 패턴이 없으면 `ADR-0001-<영문-주제>-<YYYYMMDD>.md`를 fallback으로 제안합니다. 상태·날짜·맥락·결정·결과·근거를 확인할 수 없으면 추정해서 채우지 말고 필요한 정보를 묻습니다. 대안이나 결정자가 기록되지 않았다면 해당 조건부 항목을 생략합니다.

## 의사결정 로그

되돌리기 쉽거나 영향 범위가 작은 결정을 ADR보다 가벼운 단일 로그로 관리하는 프로젝트도 있습니다. 기존 형식이 없으면 항목마다 **날짜 → 결정 → 맥락 → 영향 → 근거**를 기록합니다. 여러 영역에 오래 영향을 주거나 대안·trade-off를 보존해야 하는 결정은 로그 한 줄로 축약하지 말고 ADR로 작성합니다.

## 프로젝트 히스토리

연대순 또는 역연대순 중 기존 문서의 방식을 따릅니다. 각 전환점에는 다음 정보를 기록합니다.

- **날짜/기간**: 커밋, 태그, 릴리스 등으로 확인 가능한 범위
- **변화**: 무엇이 추가·변경·제거됐는지
- **영향**: 사용자, 개발 방식, 운영에 생긴 확인 가능한 변화
- **이유**: 이슈·ADR·사용자 설명으로 확인될 때만
- **근거**: 관련 커밋·태그·PR·문서

사소한 정리 커밋은 제외하고 여러 커밋이 하나의 변화라면 한 항목으로 묶습니다. 근거가 없는 프로젝트 초기 이야기나 의도를 서사적으로 만들어내지 않습니다.

## 사고 기록

사고 한 건당 별도 기록을 사용하고 **요약 → 영향 → 타임라인 → 확인된 원인 → 대응과 복구 → 후속 조치 → 근거** 순으로 작성합니다. 추정 원인은 확정 원인과 명확히 구분하고, 사람을 탓하는 표현 대신 시스템 조건과 관찰 가능한 사건을 기록합니다. 비밀값·개인정보·접속 정보는 포함하지 않습니다.

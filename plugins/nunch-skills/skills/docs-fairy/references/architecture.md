# 아키텍처 문서

프로젝트 아키텍처 문서를 생성하거나 구조를 개선할 때 적용하는 작성 계약입니다. 사실과 결정 근거의 권한은 [문서 공통 정책](shared-policy.md)을 따르고, ADR 본문과 양식은 [프로젝트 기록](project-records.md)이 소유합니다.

기본 독자는 서비스를 처음 접하는 신규 개발자와 기존 개발자입니다. 사용자가 운영자·보안 담당자처럼 다른 독자를 명시하면 그 요청을 우선합니다.

## 요청 범위부터 구분

- **전체 아키텍처 또는 프로젝트 개괄 요청**: 짧은 overview를 진입점으로 만들고, 설명 가치가 있는 주제만 상세 문서로 연결합니다.
- **집중 요청**: C4 그림 하나, ADR 하나, 특정 아키텍처 주제처럼 범위가 좁으면 요청한 산출물만 만듭니다. 전체 overview·detail 구조로 자동 확장하지 않습니다.

사용자가 산출물 수나 범위를 명시했다면 그 범위가 상세 그림 분리보다 우선합니다. 범위를 넘어야만 내용을 정확하게 표현할 수 있으면 임의로 확장하지 말고 필요한 방향을 묻습니다.

## 위치와 탐색 구조

먼저 기존 아키텍처 문서의 위치·파일명·링크 관례를 따릅니다. 관례가 없을 때만 다음 위치를 fallback으로 사용합니다.

- overview: `docs/architecture.md`
- 주제별 상세: `docs/architecture/<topic>.md`

overview는 다음 정보만으로 프로젝트 전체 지도를 제공합니다.

1. 시스템의 목적과 범위
2. 능동적으로 선택한 C4 개괄 그림
3. 주요 상위 구성 요소와 각 역할
4. 실제로 존재하는 상세 문서 링크
5. 관련 ADR 링크, 또는 저장소를 확인한 뒤의 `확인된 관련 ADR 없음`

상세 문서가 없으면 빈 링크 목록이나 예정 문서를 만들지 않습니다. overview, 상세 문서, ADR은 각자 소유한 정보만 원문으로 기록하고 다른 문서에서는 짧게 요약해 링크합니다. 특히 결정의 이유·대안·결과는 ADR이 소유하며 아키텍처 문서에 복제하지 않습니다.

## arc42를 선택형 구조로 사용

arc42는 고정 목차가 아니라 필요한 관점을 찾는 구조로 사용합니다. 시스템 특성, 아키텍처적 중요성, 신규·기존 개발자의 이해 필요성을 바탕으로 관련 관점만 능동적으로 선택합니다. 모든 영역을 채우거나 빈 섹션을 남기지 않습니다.

선택 가능한 관점에는 시스템 맥락과 범위, 제약, 빌딩 블록, Runtime, Deployment, 횡단 관심사, 품질 요구사항, 위험과 기술 부채가 포함될 수 있습니다. 이 목록은 필수 목차가 아닙니다. 별도의 이해관계자 표도 실제 이해에 도움이 될 때만 작성합니다.

Runtime이나 Deployment 설명은 overview의 필수 항목이 아닙니다. 중요한 실행 흐름·장애 경로·프로세스 경계·배포 토폴로지를 이해하는 데 필요하거나 사용자가 요청했을 때 상세 문서에 추가합니다.

## C4 그림 선택과 품질

C4의 정적 추상화 수준은 System Context, Container, Component, Code 중 필요한 수준을 최대 네 가지 범위 안에서 능동적으로 선택합니다. 기본 수준, 필수 개수, 단계별 고정 선택 규칙을 두지 않습니다. Code 수준은 사용자가 요청했거나 중요한 아키텍처를 설명하기 위해 반드시 필요할 때만 제공합니다.

Runtime 흐름이나 Deployment 구조가 중요하면 C4 Dynamic·Deployment 또는 프로젝트가 이미 지원하는 호환 흐름·배포 그림을 사용할 수 있습니다. 이 그림들은 정적 네 수준을 모두 작성하게 만드는 근거가 아닙니다.

각 그림은 다음 계약을 지킵니다.

- 하나의 C4 추상화 수준과 하나의 설명 목적만 다룹니다.
- 제목과 선택한 C4 유형·범위를 표시합니다.
- 각 요소의 이름과 역할을 표시합니다.
- 관계의 방향과 목적을 표시합니다.
- 복잡한 내용은 요청 범위 안에서 별도 상세 그림으로 분리합니다.

C4는 의미 모델이고 Mermaid 같은 형식은 표현 수단입니다. 기존 문서 renderer가 지원하는 형식을 사용하며, 이를 위해 새 renderer나 다이어그램 도구를 자동 도입하지 않습니다. 변동이 큰 하위 수준 그림에 기존 source-backed 생성 방식이 있으면 수작업 복제보다 그 방식을 우선 재사용합니다.

## ADR 연결

아키텍처 문서 생성은 ADR 생성 권한을 포함하지 않습니다. 관련 ADR이 있으면 링크하고, 확인되지 않은 결정 이유를 코드 형태에서 추론하지 않습니다. 관련 ADR이 없더라도 사용자가 기록을 요청하지 않았다면 새 ADR을 만들지 않습니다.

사용자가 ADR 생성을 요청한 경우에만 `RECORD`로 처리하고 [ADR 계약과 fallback 양식](project-records.md#adr)을 따릅니다.

## 작성 절차

1. 요청을 전체 아키텍처 요청과 집중 요청 중 하나로 구분합니다.
2. 코드·설정·테스트·기존 문서·ADR에서 현재 구조와 확인된 결정 근거를 조사합니다.
3. 기존 문서 관례를 확인하고, 전체 요청일 때만 overview와 필요한 상세 문서의 정보 소유권을 나눕니다.
4. 필요한 arc42 관점과 C4 수준을 능동적으로 선택합니다.
5. 선택한 문서만 작성하고 실제 문서끼리 연결합니다.
6. 사실, 링크, 그림과 코드·설정의 일치를 검증합니다.
7. 결과 보고에 선택한 C4 수준과 주요 생략 판단의 이유를 짧게 남깁니다.

기존 아키텍처 문서를 새 구조로 전면 재구성하는 작업은 사용자가 명시적으로 요청한 경우에만 수행합니다.

## 완료 확인

- 전체 요청의 overview에서 목적·범위와 주요 구조를 한눈에 파악할 수 있습니다.
- 실제 상세 문서와 관련 ADR만 탐색 가능한 링크로 연결됩니다.
- 선택한 arc42 관점과 C4 수준이 독자와 시스템에 필요한 만큼만 존재합니다.
- 각 C4 그림의 수준·목적·범위·요소·관계가 명확합니다.
- overview·상세·ADR 사이에 서로 다르게 낡을 정보가 복제되지 않았습니다.
- 문서의 시스템 경계·외부 연동·주요 구성 요소·Runtime·Deployment 설명이 코드와 설정에 부합합니다.

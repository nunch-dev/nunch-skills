# 문서 생성 (GENERATE)

새 문서를 만들 때의 공통 절차와 문서 유형별 지침입니다.

## 공통 절차

1. **코드베이스 조사부터.** 문서를 쓰기 전에 대상을 직접 읽습니다 — entry point, 설정 파일, package manifest, 테스트, 기존 문서. 조사 없이 템플릿부터 채우면 그럴듯한 거짓말이 됩니다.
2. **기존 문서 확인.** 같은 주제를 다루는 문서가 이미 있으면 새로 만들지 말고 그 문서를 갱신할지 사용자에게 확인합니다. 중복 문서는 반드시 한쪽이 낡습니다.
3. **위치 결정.** 프로젝트에 docs/ 디렉터리나 문서 사이트가 있으면 그 구조를 따릅니다. 없으면 관례적 위치(README는 루트, 설계 문서는 docs/)를 씁니다.
4. **작성 후 자체 검증.** 문서의 모든 명령어·경로·옵션을 코드와 다시 대조합니다. 실행 가능한 명령은 실행해봅니다(설치·삭제 등 부작용 있는 명령 제외).

## Diátaxis에 맞춘 작성 템플릿

새 페이지를 만들거나 여러 목적이 섞인 문서를 재구성할 때 주된 독자 요구를 하나 고르고, [The Good Docs Project의 문서 유형](https://www.thegooddocsproject.dev/template)을 Diátaxis에 맞춰 다음처럼 적용합니다. 템플릿은 필요한 내용을 빠뜨리지 않기 위한 출발점이지 모든 항목을 채우는 고정 목차가 아닙니다.

| 유형 | 독자가 원하는 것 | 기본 구조 |
|---|---|---|
| **Tutorial** | 안내를 따라 배우며 첫 성공 경험 얻기 | 학습 결과 → 전제 조건 → 순서대로 이어지는 실습 → 단계별 확인 → 다음 학습 경로 |
| **How-to guide** | 이미 아는 상황에서 구체적인 목표 달성하기 | 목표와 조건 → 번호가 있는 절차 → 기대 결과 → 실패 시 확인할 항목 |
| **Reference** | 정확한 사실을 빠르게 조회하기 | 범위 → 일관된 항목 형식 → 타입·기본값·제약 → 최소 예제와 관련 항목 |
| **Explanation** | 개념·맥락·이유와 상호작용 이해하기 | 설명할 질문 → 배경과 핵심 개념 → 작동 관계·근거·trade-off → 관련 실습·레퍼런스 링크 |

README와 문서 사이트 홈처럼 여러 독자 요구로 안내하는 진입 문서는 예외적으로 여러 유형을 담을 수 있습니다. 이 경우 빠른 시작, 목적별 절차, 조회 정보, 배경 설명을 섹션으로 분리하고 상세 페이지로 연결합니다. Troubleshooting은 증상 하나를 해결하는 how-to로 작성하되 **증상 → 확인된 원인 → 해결 절차 → 정상 결과**의 순서를 사용합니다.

## 시각 우선 입문자 설명

사용자가 "쉽게 설명해줘", "비개발자도 이해하게", "그림으로 보여줘"처럼 요청했거나 문서의 명시적 독자가 입문자라면 Diátaxis의 **tutorial** 또는 **explanation**에 시각 우선 설명을 적용합니다. 일반 how-to, API/CLI reference, CHANGELOG, 런북에는 이 표현 방식을 자동 적용하지 않습니다.

1. **한눈에 보기부터.** 독자가 세부 용어를 몰라도 전체 흐름을 잡을 수 있는 Mermaid 다이어그램 하나와 핵심 문장 2~4개를 먼저 둡니다. 한 그림에는 핵심 개념 하나만 담고 라벨은 짧게 씁니다.
2. **쉬운 말 다음에 정확한 말.** 일상어로 먼저 설명한 뒤 실제 코드·설정에서 쓰는 기술 용어를 소개합니다. 유아적인 말투나 정확한 용어의 삭제는 피합니다.
3. **비유의 경계 표시.** 비유가 도움이 될 때만 사용하고, 실제 동작과 달라지는 지점이 중요하면 바로 밝혀 오해를 막습니다.
4. **상세 정보는 아래 계층으로.** 시각 요약이 정확한 설명을 대체하지 않도록 검증된 동작, 제약, 예외를 뒤에 둡니다. reference가 필요하면 같은 페이지에 섞지 말고 별도 문서로 연결합니다.
5. **출력 형식 존중.** Markdown이나 Starlight 문서는 Mermaid와 해당 문서 시스템의 컴포넌트를 사용합니다. 사용자가 독립 HTML explainer를 명시적으로 요청한 경우에만 HTML artifact를 만듭니다.

## README

독자는 "이 프로젝트가 뭔지 30초 안에 알고, 5분 안에 돌려보고 싶은 사람"입니다.

권장 구성 (이 순서로):

```markdown
# 프로젝트명
한 문장 소개 — 무엇을, 누구를 위해, 왜.

## 요구 사항 (해당 시)
런타임 버전, 필수 도구 등 전제 조건.

## 설치
실제 동작 확인한 설치 명령.

## 빠른 시작
대표 시나리오 하나를 처음부터 끝까지 — 명령과 기대 출력을 함께.
독자가 이 블록만 따라 하면 동작하는 경험을 얻어야 합니다.

## 명령어 / 옵션
명령이나 옵션이 여러 개면 반드시 마크다운 표로 정리합니다
(| 명령어 | 설명 | 옵션·기본값 | 형태). 각 명령에 설명할 내용이 많으면
표 아래(또는 명령별 하위 섹션)에 상세를 붙입니다.

## 그 외 실제로 있는 것들
데이터/설정 파일 위치, 테스트 실행 방법, 라이선스 등 —
프로젝트가 실제로 갖춘 것만, 코드·manifest에서 확인해서.

## 주의사항 (해당 시)
독자가 걸려 넘어질 함정(첫 실행 전 준비 작업, 알려진 제약 등)은 본문
문단에 녹이지 말고 별도 섹션에 목록으로 모읍니다.
```

주의사항을 별도 섹션으로 두는 이유: 문단 속에 녹이면 항목이 늘어날 때 흩어져서 찾을 수 없게 되지만, 목록 섹션이면 몇 개가 되든 한 곳에 쌓입니다. 관련 본문 위치(설치 절차 등)에는 한 줄 언급 + 섹션 참조만 남깁니다.

간결함은 "섹션을 줄이는 것"이 아니라 "각 섹션에서 군더더기를 빼는 것"입니다. 독자가 실제로 찾을 정보(테스트 방법, 데이터 저장 위치 등)를 담은 섹션은 문서를 길게 만들어도 값을 합니다. 반대로 배지, 이모지 장식, "Features" 나열식 마케팅 문구는 정보가 없으므로 사용자가 요청할 때만 넣습니다.

## 아키텍처/설계 문서

독자는 "이 코드베이스를 처음 고치려는 개발자"입니다. 목표는 코드를 읽기 전에 지도를 주는 것.

- **구조보다 흐름.** 디렉터리 나열보다 대표 시나리오 하나가 모듈을 어떻게 통과하는지(요청→처리→응답)를 보여줍니다.
- **결정과 이유.** "왜 이렇게 했는가"를 기록합니다 — 선택한 방식, 고려했다 버린 대안, 제약 조건. 코드에서 읽을 수 없는 정보라 문서의 존재 이유입니다. 이유를 모르면 지어내지 말고 git log·커밋 trailer를 조사하거나 사용자에게 묻습니다.
- **다이어그램.** 모듈 관계·흐름은 mermaid로 그립니다. 3개 이하 박스면 다이어그램 없이 산문으로 충분합니다.
- 파일명 예: `docs/architecture.md`, `docs/design/auth-flow.md`

## API/CLI 레퍼런스

독자는 "특정 함수/명령의 정확한 시그니처를 찾으러 온 사람"입니다. 완전성과 정확성이 전부입니다.

- **소스에서 추출.** 시그니처·옵션·기본값은 코드에서 직접 추출합니다. CLI라면 `--help` 출력을 실행해 대조합니다.
- **항목 형식 통일**: 이름 → 한 줄 설명 → 시그니처/사용법 → 매개변수·옵션 표(이름, 타입, 기본값, 설명) → 예제 1개 → 주의사항(있을 때만).
- **누락 없이.** 레퍼런스는 부분 작성이 무의미합니다. 범위가 크면 진단 단계에서 대상 목록을 보고하고 범위를 합의합니다.

## 스킬·플러그인 카탈로그

독자는 "어떤 스킬을 언제 불러야 하고, 호출하면 무엇이 달라지는가"를 빠르게 판단하려는 사용자입니다.

- **인벤토리부터 확정.** 플러그인 manifest와 실제 `skills/*/SKILL.md`를 함께 확인합니다. manifest에 선언됐지만 파일이 없거나, 파일은 있지만 배포 대상이 아닌 항목을 같은 목록에 섞지 않습니다.
- **진입점과 본체 구분.** 짧은 명령 wrapper와 실제 workflow를 소유한 primary skill을 별개로 설명하고 관계를 밝힙니다.
- **목록은 선택을 돕는 표로.** 스킬명, 쓰는 상황, 사용자에게 남는 결과, 상세 문서 링크를 한 표에 둡니다.
- **개별 페이지는 사용자 관점으로.** 한 문장 목적, 사용 시점과 비대상, 실제 호출 예, 핵심 흐름, 권한·안전 경계와 필수 의존성, source 링크를 필요한 만큼만 담습니다. 내부 agent 이름이나 중간 artifact는 사용자가 실행·문제 해결에 필요할 때만 설명합니다.
- **충돌을 숨기지 않음.** SKILL.md와 연결된 workflow가 서로 다른 파일명·단계·동작을 말하면 한쪽을 임의로 정답 처리하지 않습니다. 확인된 범위만 설명하고, 따라 하면 실패할 수 있는 충돌은 불일치로 진단합니다.
- **원문 복제 금지.** `SKILL.md` 전체를 다시 풀어 쓰지 않습니다. 선택과 첫 사용에 필요한 정보만 문서화하고 상세 실행 계약은 source로 연결합니다.

## CHANGELOG/릴리스 노트

- git log를 근거로 작성하되, 커밋 나열이 아니라 **사용자 관점 변화**로 묶습니다: 추가/변경/수정/제거.
- Breaking change는 맨 위에, 마이그레이션 방법과 함께.
- 기존 CHANGELOG 형식(Keep a Changelog 등)이 있으면 따릅니다.

## 런북 (운영 문서)

독자는 "장애 중이거나 배포 중인, 시간에 쫓기는 사람"입니다.

- 절차는 번호 목록으로, 각 단계는 실행할 명령 + 기대 결과("이 명령 후 X가 보여야 함").
- 판단 분기는 명시적으로: "A가 보이면 3단계로, 아니면 5단계로."
- 전제 조건(권한, 접속 정보의 위치 — 값 자체는 절대 문서에 넣지 않음)을 맨 위에.

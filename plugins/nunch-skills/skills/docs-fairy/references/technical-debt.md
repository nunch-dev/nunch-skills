# 기술부채 기록과 해소 가이드

문서 감사·동기화·SITE 작업에서 바로 해소하지 못한 문제를 경고로만 남기지 않고 다음 작업자가 실제로 끝낼 수 있는 형태로 기록합니다. 기술부채 기록은 hard gate를 우회하는 수단이 아닙니다. build나 production preview처럼 현재 mode가 필수로 정한 gate가 실패했다면 기술부채를 작성해도 완료로 판정하지 않습니다.

## 적용 시점

다음 상황에서 이 reference를 읽습니다.

- 문서와 코드, 원본과 사이트 사본 사이의 drift를 바로 해소하지 못한다.
- 반복 수작업, 임시 우회, 불안정한 설정이나 미검증 warning을 남긴다.
- AUDIT·SYNC·SITE 결과에 후속 해소가 필요한 항목이 있다.
- 사용자가 기술부채의 영향과 해소 경로를 문서화해 달라고 요청한다.

docs-fairy는 기술부채의 해소 방법을 안내할 수 있습니다. 직접 수정하는 범위는 문서와 docs-site이며 일반 애플리케이션 코드·다른 package 구현·비문서 설정은 수정하지 않습니다. 이슈 생성은 `git-tools`의 역할입니다. docs-fairy는 이슈·assignee·label·milestone을 만들거나 바꾸지 않습니다.

## 기록 강도

| 강도 | 항목 | 규칙 |
|---|---|---|
| 필수 | 영향 범위 | 영향을 받는 문서·사용자 흐름·package·배포 단계 중 하나 이상 |
| 필수 | 영향 | 방치하면 생기는 문제를 비전문 사용자도 이해할 수 있게 설명 |
| 필수 | 심각도 | `Critical`·`High`·`Medium`·`Low` 중 하나 |
| 필수 | 권장 목표 상태 | 해소 후 도달해야 할 상태 |
| 필수 | 해소 절차 | 목표 상태까지 이어지는 순서 있는 단계 |
| 필수 | 선행 조건 | 필요한 조건을 적고 없으면 `없음` |
| 필수 | blocker | 현재 해소를 막는 요소를 적고 없으면 `없음` |
| 필수 | 검증 방법 | 명령·production preview 흐름·비교·점검 등 확인 방법 |
| 필수 | 종료 기준 | 사람이 바뀌어도 같은 결론을 낼 수 있는 관찰 가능한 결과 |
| 필수 | 담당 주체 | 기본값은 `미지정`. 명시된 사람·팀·역할만 기록 |
| 강력 권장 | 근거 | 코드·설정·build 결과·production preview 관찰처럼 다시 확인할 수 있는 자료 |
| 권장 | 재검토 조건 | 상태 변화·의존성 해소 등 다시 검토하게 만드는 trigger |
| 선택 | 재검토 날짜 | 근거 있는 일정이 있을 때만 기록 |
| 선택 | 재검토 상태 | 필요하면 `미정`으로 표시 |

근거가 없어도 발견 단계의 기술부채를 기록할 수 있습니다. 다만 확인된 사실처럼 단정하지 말고 `미검증`으로 표시한 뒤 근거를 확보하지 못한 이유와 다음 검증 방법을 함께 적습니다.

## 영향 작성

결함 이름만 적지 말고 사용자가 겪는 결과를 설명합니다. 이미 관찰된 영향과 앞으로 발생할 수 있는 위험·우려를 구분하며 가능성을 확정된 사실처럼 과장하지 않습니다.

```markdown
확인된 영향: 사이트의 편집 링크가 정본이 아닌 사본을 열어 수정 내용이 원본에 반영되지 않는다.
잠재 위험: 두 사본의 차이가 커지면 사용자가 서로 다른 설치 절차를 보게 될 수 있다.
```

## 심각도

심각도는 수정 난이도나 예상 공수가 아니라 방치했을 때의 결과로 판단합니다. 처리 우선순위와 완료 차단 여부는 별도입니다. 여러 요소의 평균으로 등급을 낮추지 말고 확인된 결과 중 가장 중대한 것을 기준으로 삼습니다.

| 등급 | 판정 기준 |
|---|---|
| `Critical` | 필수 build·production preview·배포 또는 문서의 핵심 사용을 막거나, 보안·데이터 손실·되돌리기 어려운 행동을 유발할 수 있는 위험한 오정보가 있어 즉시 대응해야 함 |
| `High` | `Critical` 수준의 즉각적·되돌리기 어려운 피해나 전체 차단은 아니지만 핵심 사용자 흐름 또는 문서 신뢰성이 크게 훼손되고 신뢰할 만한 우회가 없거나 불안정함 |
| `Medium` | 영향 범위가 제한되고 핵심 사용을 막지 않으며 신뢰할 수 있는 우회가 있지만 drift·반복 수작업·유지보수 비용이 누적되어 계획적인 해소가 필요함 |
| `Low` | 현재 사용자 흐름·문서 신뢰성·build·배포에 실질적인 장애가 없고 국소적인 일관성·가독성 또는 작은 유지보수 불편을 개선하는 수준임 |

판단 근거가 충분하지 않으면 현재 가장 타당한 추정 등급에 `provisional`을 붙입니다. 후속 검증 방법을 기록하고 검증 전에는 확정 등급처럼 사용하지 않습니다.

등급 자체로 완료 여부를 정하지 않습니다. 예를 들어 production preview 실패는 실제로 `local-complete` hard gate를 위반했기 때문에 차단되는 것이지 `Critical`이라는 이름 때문에 차단되는 것이 아닙니다.

## 검증 방법과 종료 기준

두 항목을 분리합니다.

- **검증 방법**은 어떻게 확인할지 설명합니다. 예: `pnpm build`, production preview에서 검색 결과 진입, 원본과 생성본 diff 비교.
- **종료 기준**은 어떤 결과가 나오면 해소됐다고 판정할지 설명합니다. 가능하면 pass/fail로 작성합니다.

`문제가 없어 보임`, `적절히 정리됨`처럼 관찰할 수 없는 표현은 종료 기준이 아닙니다. 종료 기준을 실제로 검증하지 못한 항목은 열린 상태로 유지합니다.

## 담당 주체와 재검토

`담당 주체` 필드는 항상 두되 기본값은 `미지정`입니다. 사용자 설명이나 프로젝트 자료에 담당자가 명시돼 있을 때만 사람·팀·역할을 적습니다. AI가 담당자를 추론하거나 임의로 배정하지 않습니다. `미지정`이어도 기술부채 기록은 유효합니다.

재검토 조건은 권장합니다. 의존성 업그레이드, provider 선택, 원본 통합처럼 다시 판단해야 하는 상태 변화를 적습니다. 구체적인 날짜와 `미정` 표기는 선택 사항이며 재검토 정보가 없다는 이유만으로 기록이나 완료를 차단하지 않습니다. 자동 알림과 일정은 만들지 않습니다.

## 기록 템플릿

```markdown
### TD-{식별자}: {제목}

- 상태: open
- 근거: {경로·명령 결과·preview 관찰 또는 `미검증`}
- 근거 미확보 이유: {근거가 없을 때만}
- 영향 범위: {문서·사용자 흐름·package·배포 단계}
- 확인된 영향: {쉬운 표현으로 작성}
- 잠재 위험 또는 우려: {없으면 `없음`}
- 심각도: {Critical|High|Medium|Low}{근거가 부족하면 뒤에 `provisional` 표시}
- 권장 목표 상태: {해소 후 상태}
- 해소 절차:
  1. {첫 단계}
  2. {다음 단계}
- 선행 조건: {조건 또는 `없음`}
- blocker: {요소 또는 `없음`}
- 검증 방법: {명령·preview·비교·점검}
- 종료 기준: {관찰 가능한 pass/fail 결과}
- 담당 주체: {명시된 사람·팀·역할 또는 `미지정`}
- 재검토 조건: {권장, 없으면 생략 가능}
- 재검토 날짜: {선택}
```

## 결과 보고

완료 보고에서는 기술부채를 숨기거나 일반 warning 목록에 묻지 않습니다. 항목별로 심각도, 영향, 목표 상태, 다음 해소 단계와 현재 blocker를 보여줍니다. 항목이 많으면 등급·영향 범위별로 묶되 필수 필드는 원본 기록에서 확인할 수 있어야 합니다.

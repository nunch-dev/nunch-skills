# Docs Fairy

일반 문서 요청의 primary router입니다. 작업을 시작할 때 권한·근거·표현·검증·보고의 규범 원본인 [문서 공통 정책](references/shared-policy.md)을 읽습니다.

이 스킬이 직접 수정하는 범위는 일반 문서 파일입니다. 문서 사이트의 scaffold·콘텐츠 통합·설정·package·build·preview·배포는 [`docs-fairy-site`](../docs-fairy-site/SKILL.md)가 소유합니다. 일반 애플리케이션 코드, 다른 package 구현, 비문서용 저장소 설정은 수정하지 않고 필요한 해소 방법만 안내합니다. 이슈 생성은 이 스킬의 역할이 아니므로 이슈·assignee·label·milestone을 직접 변경하지 않습니다.

## 일반 문서 전용 변경 절차

문서 오류는 자동으로 드러나지 않은 채 독자의 행동을 잘못 이끌 수 있습니다. **WHEN** `SYNC`·`AUDIT`·넓은 `IMPROVE` 조사에서 변경 후보를 새로 발견하면, 에이전트는 파일을 수정하지 않고 먼저 진단 목록을 제시합니다. **IF** 사용자가 항목 번호를 선택하면 선택된 항목만 수정합니다. 그 밖의 변경 권한과 범위 확대 조건은 공통 정책을 그대로 적용합니다.

넓은 조사에서 발견한 변경 후보는 [진단 보고 형식](references/diagnosis-report.md)으로 먼저 보고합니다. 불일치, 필수 누락, 선택적 보강을 구분하고 모든 항목에 코드 위치나 커밋 근거를 붙입니다. 해소되지 않은 기술부채를 기록하거나 완료 상태에 남길 때는 [기술부채 기록과 해소 가이드](references/technical-debt.md)를 함께 읽습니다.

### 수정 후 결과 보고

승인받아 수정한 뒤에는 무엇을 어떻게 바꿨는지 보고합니다. 보고의 상세 수준은 변경 규모에 맞춥니다.

- 항목이 적으면(대략 10건 이하): 항목별로 "어느 문서의 무엇을 어떻게" 수준까지 상세히.
- 대규모면(큰 개발 뒤의 일괄 갱신 등): 문서별·유형별로 묶어 요약하고 대표 예시 몇 개만 상세히 보여줍니다. 수십 건을 전부 나열하면 사용자가 검토할 수 없으므로, 필요하면 diff 확인 방법(`git diff` 등)을 안내합니다. 이런 규모라면 애초에 진단 단계에서 묶음 단위로 나눠 승인받는 것을 먼저 제안합니다.

문서를 새로 만들었을 때의 결과 보고에서는 핵심 구조물(명령어 표, 옵션 표 등)을 산문으로 요약하지 말고 **문서에 넣은 표를 그대로 발췌해** 보여줍니다. 사용자는 대부분 보고만 보고 승인 여부를 정하므로, 보고에서 표가 안 보이면 문서에 표가 없다고 판단하게 됩니다.

## Router

요청의 주된 작업을 하나 선택하고 필요한 reference만 읽습니다.

| Mode | 요청 예 | 읽을 reference |
|---|---|---|
| `GENERATE` | README/아키텍처 문서/API·CLI 레퍼런스/CHANGELOG/런북을 새로 작성 | [문서 생성](references/generation.md) |
| `RECORD` | ADR, 의사결정 로그, 프로젝트 히스토리, 사고 기록 작성·갱신 | [프로젝트 기록](references/project-records.md) |
| `SYNC` | "문서가 코드랑 맞는지 확인", 코드 변경 후 문서 갱신 | [동기화와 감사](references/sync.md)의 `SYNC` |
| `AUDIT` | "문서 전체 점검해줘", 주기적 문서 감사 | [동기화와 감사](references/sync.md)의 `AUDIT` |
| `IMPROVE` | "문서 읽기 좋게 다듬어줘", 구조·명확성 개선 | [품질 개선](references/quality.md) |

일반 문서 작업이 여러 mode에 걸치면 primary 하나를 정하고 실제로 필요한 reference만 추가로 읽습니다.

## `docs-fairy-site`로 전환

**WHEN** 요청의 결과가 문서 사이트 scaffold·통합·build·preview·배포이면 일반 문서 mode로 처리하지 말고 [`docs-fairy-site`](../docs-fairy-site/SKILL.md)를 읽어 같은 turn에서 전환합니다. 이 스킬은 분류와 handoff만 수행하며 SITE workflow를 중복 실행해서는 안 됩니다.

**WHEN** 한 요청에 일반 문서 생성·수정과 SITE 작업이 함께 있으면 다음 순서를 사용합니다.

1. 이 스킬이 일반 문서를 먼저 생성·수정하고 [문서 공통 정책](references/shared-policy.md)의 검증을 완료합니다.
2. 검증된 산출물과 미검증 항목을 구분합니다.
3. **IF** SITE에 필수인 산출물이 누락됐거나 미검증이면 SITE로 전환하지 않고 사용자의 선택을 요청합니다.
4. **ELSE** 검증된 산출물만 `docs-fairy-site`에 넘기고, 필수가 아닌 미검증 항목을 명시한 뒤 같은 turn에서 SITE workflow를 한 번 실행합니다.

예시:

- 입력: “`docs-fairy`로 API 문서를 쓰고 사이트도 만들어줘.”
- 판단: `GENERATE` 완료 후 SITE handoff가 필요한 복합 요청입니다.
- 기대 행동: API 문서의 명령·경로·API를 검증한 뒤 `docs-fairy-site`로 한 번 전환합니다. API 문서가 검증되지 않으면 사이트 생성을 시작하지 않고 한 가지 선택을 묻습니다.

### 자동 한국어 윤문

한국어 문서를 새로 작성하거나 본문을 실질적으로 재작성한 뒤 현재 환경에서 호출할 수 있거나 사용자가 로컬 사용을 허용한 `humanize-korean` 후보가 있으면, 사실·구조 검증을 마친 초안에 [한국어 윤문 연동](references/korean-humanization.md)을 마지막 단계로 자동 적용합니다. 후보는 경로·버전이 아니라 실제 실행 사전 점검으로 선택합니다. 쓸 수 있는 후보가 없으면 기존 흐름을 그대로 완료하며 설치를 요구하거나 작업을 중단하지 않습니다. 진단 보고, 문서 찾기, 오타 한두 건처럼 새 산문을 만들지 않는 작업에는 적용하지 않습니다.

### 경량 요청

다음은 reference 없이 이 파일의 규칙만으로 바로 처리합니다.

- **지목된 오타·자잘한 수정** ("README 12번째 줄 오타 고쳐줘"): 범위가 명확한 단일 수정이므로 진단 보고 없이 바로 고치고 결과만 알립니다. 고치는 김에 발견한 다른 문제는 수정하지 말고 진단 항목으로만 보고합니다.
- **문서 번역**: 내용·구조는 그대로 두고 언어만 바꿉니다. 코드 식별자·명령어는 원문 유지, 대상 언어 관례(경어체 등)는 기존 문서를 따르고, 기존 문서를 대체할지 병렬 파일(`README-en.md` 등)로 둘지는 요청이 불명확하면 확인합니다.
- **문서 찾기·안내** ("온보딩 문서 어디 있어?"): read-only 조사로 위치와 한 줄 요약만 답합니다. 조사 중 낡은 내용을 발견하면 답과 함께 알리되 수정은 승인 후에 합니다.

## 완료 조건

완료 판정은 [문서 공통 정책](references/shared-policy.md)의 검증과 완료 조건을 따릅니다. 일반 문서 작업은 추가로 변경 범위, 남은 staged·unstaged 문서 변경과 미해결 진단 항목을 보고합니다.

실패 예시:

- 입력: “CLI 문서를 현재 코드와 맞춰줘.”
- 관찰: 문서는 수정했지만 `docs:links`가 깨진 내부 링크로 실패했습니다.
- 기대 행동: 링크 실패를 숨기거나 완료라고 보고하지 않습니다. 수정된 문서, 통과한 검증, 실패한 명령과 남은 링크를 `partial success`로 보고합니다.

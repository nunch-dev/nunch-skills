# docs-fairy

## 개요

코드베이스와 프로젝트 이력을 근거로 일반 문서를 생성·기록·동기화·감사·개선·번역하는 스킬입니다. 현재 동작은 코드에서, 변경 시점은 Git 이력에서, 결정 이유는 ADR·이슈·사용자 설명에서 확인합니다.

문서 사이트의 scaffold·콘텐츠 통합·설정·build·preview·배포는 연관 스킬인 [`docs-fairy-site`](docs-fairy-site.md)가 담당합니다.

## 사용 시점

- README, 아키텍처·설계 문서, API·CLI 레퍼런스, CHANGELOG, 런북을 작성할 때
- ADR·의사결정 로그·프로젝트 히스토리·사고 기록을 남길 때 (`RECORD`)
- 코드 변경 후 낡은 문서를 찾을 때 (`SYNC`) 또는 문서 전체를 점검할 때 (`AUDIT`)
- 기존 문서의 구조·명확성을 개선하거나 문서를 번역·탐색할 때

코드 주석·커밋 메시지·PR 설명, 외부 공식 문서 조회, 문서 스펙 기반 코드 생성, 일반 코드 디버깅에는 사용하지 않습니다.

## 사용 예

```text
$docs-fairy 이 플러그인에 포함된 각 스킬의 용도와 사용 시점을 문서로 정리해줘
```

## 핵심 계약

- 사용자가 대상과 변경을 명확히 지정하면 그 범위의 일반 문서를 바로 수정합니다.
- `SYNC`·`AUDIT`·넓은 `IMPROVE`에서 새로 발견한 후보는 근거가 있는 진단 목록으로 먼저 제시하고, 사용자가 선택한 항목만 수정합니다.
- 최초 요청에 없던 삭제·전면 재작성·대규모 구조 변경·rename은 대상과 영향을 보여주고 별도 승인을 받습니다.
- 명령·옵션·경로는 코드에서, 변경 이력은 Git 기록에서, 결정 이유는 기존 기록이나 사용자 설명에서 확인합니다. 코드만 보고 과거 의도를 추정하지 않습니다.
- ADR의 이전 결정은 지우지 않고 `Superseded` 상태와 후속 ADR 링크로 보존합니다.

## 문서 사이트로 전환

“docs site를 만들어줘” 같은 자연어 요청은 `docs-fairy-site`가 직접 처리합니다. 사용자가 `$docs-fairy`를 지정했더라도 요청 결과가 문서 사이트이면 같은 응답 안에서 `docs-fairy-site`로 한 번만 전환합니다.

일반 문서와 사이트를 함께 요청하면 `docs-fairy`가 문서를 먼저 작성·검증합니다. 사이트에 필수인 문서가 누락됐거나 검증되지 않았으면 사이트 작업을 시작하지 않고 사용자의 선택을 요청합니다. 그 외에는 검증된 문서만 넘기고 남은 미검증 항목을 함께 보고합니다.

## 완료 조건

문서의 사실과 출처가 일치하고, 문서에 적은 경로·명령·API가 실제로 존재하며, 저장소에 관련 lint·link check·build가 있으면 통과해야 완료입니다. 필요한 검증을 실행하지 못했거나 실패하면 완료라고 하지 않고 검증된 결과와 남은 항목을 `partial success`로 보고합니다.
